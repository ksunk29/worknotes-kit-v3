# 작업 규칙 (worknotes-kit)

- 코딩 전에 먼저 정리한다: ①명시된 요구 ②미확인 정보 ③가정 ④완료 기준(개선 과제면 기존 수치와 계산식, 곧 기준선 포함). 미확인은 사실처럼 쓰지 말고 확인할 질문으로 남긴다.
- 업무 기준이 모호하면 추측으로 확정하지 않는다. 담당자에게 물을 질문을 만들고, 답을 받기 전에는 "확인 전 가정"이라고 코드 주석과 문서에 표시한 잠정 구현을 쓴다. 필수 필드·인터페이스는 명세를 따르고, 값을 모르면 명세가 허용하는 미확정·오류 상태로 처리한다. 필드를 채우려고 사실이나 데이터를 만들어내지 않는다.
- 요구에 없는 기능·추상화·의존성·과한 방어 코드는 추가하지 않는다. 가장 작은 변경으로 시작한다.
- 원본 데이터 파일은 수정하지 않는다. 변환 결과는 별도 파일이나 출력으로 만든다.
- 결과를 바꾸는 선택은 선택지와 추천을 내고 사용자가 고르게 하며, 이유와 대안을 `TASK.md` 설계 선택 표에 기록한다.
- 완료라고 말하기 전에 실제로 실행해 확인한다. 실행하지 않았거나 실패한 것은 "미검증"·"실패"라고 쓰고 통과라고 쓰지 않는다. 테스트 통과와 요구사항 충족은 다르다.
- 오류가 나면 추측으로 계속 고치지 않는다. 재현 → 원인 가설과 근거 → 최소 수정 → 같은 조건으로 재검증 순서로 진행하고, 3번 실패하면 접근을 다시 검토한다.
- 요청에 명시되지 않은 삭제·덮어쓰기·제출 확정·외부 전송처럼 되돌리기 어려운 행동은 실행 전에 확인한다(요청 범위에 이미 포함된 행동은 다시 묻지 않는다). 결과에 동의한 것과 그 행동을 허락한 것은 다르다. 환경이 막은 것은 승인이 있어도 다른 경로로 우회하지 않고 막혔다고 보고한다.
- 키·토큰 같은 비밀값을 코드·로그·문서에 쓰지 않고, 문제·데이터·결과물을 외부로 보내지 않는다.
- 작업이 길어져 맥락이 압축되었거나 중단 후 재개할 때는 상태 문서(`WORK.md` 등)가 있으면 먼저 읽고 현재 위치·결정·다음 행동을 확인한다. 상태 문서는 그대로 두면 다음 판단을 그르칠 때만 고치고 작은 진척마다 쓰지 않는다.
- 문서에는 실제로 한 일과 확인한 결과만 쓴다. 과제가 요구하는 제출 문서가 있으면 그 이름·경로의 실제 파일에 쓰고(심볼릭 링크·이동 금지), `TASK.md` 같은 별도 문서는 과제가 클 때만 만든다.
- 웹 서비스는 서버를 `0.0.0.0`에 바인딩하고 실제 포트를 출력한다. 서버를 띄운 터미널은 닫지 않고 같은 서버를 중복 실행하지 않는다. 응답·API는 `curl`이나 테스트로, 화면은 허용된 브라우저 자동화(별도 포트·임시 DB)와 응시자의 미리보기로 확인한다. 호스트·포트·경로는 과제 안내가 우선이다.
- 토큰을 아낀다: 데이터는 통째로 읽거나 출력하지 않고 행 수·헤더·요약으로 본다. 테스트·설치는 조용한 옵션으로 돌려 필요한 줄만 본다. 보고는 변경 파일과 짧은 요약으로 하고, 끝에 사용자가 다음에 할 일을 한 줄로 적는다.
- 세션 여럿이면 `WORK.md`의 담당 파일 밖은 고치지 않고 공통 계약(API·스키마) 변경은 먼저 기록한다. 실험은 복사본·버전 플래그에서 하고 메인은 늘 실행 가능하게 둔다.
