# 탐색·최적화: 먼저 유효한 답, 그다음 개선

최적해를 찾는 데 시간을 다 쓰지 않는다. 제약을 만족하는 답을 먼저 확보해 저장하고, 남은 시간에 같은 조건으로 개선한다.

1. 구현 전에 `TASK.md` "탐색·최적화 문제 구조"를 채운다: 결정 변수와 그 유형(이산/연속/혼합), 필수 제약, 선호 조건(점수 반영 방식), 평가 목표(계산식), 입력 규모(후보 수와 조합 수 추정), 실행 제한(시간·메모리·도구, 제한 시간에 입력 처리·검증·저장이 포함되는지), 유효해를 못 찾았을 때와 해가 없을 때의 처리. 필수/선호 구분과 목표의 가중치는 담당자 답 없이 정하지 않고 미확인·설계 선택으로 둔다.
2. **독립 검증기를 먼저 만든다.** 원본 입력과 최종 결과만 읽어 다시 계산한다: 필수 제약 위반, 누락·중복·범위 밖 값, 총량·비용 집계, 목적값 재계산. 탐색기의 점수나 내부 상태를 쓰지 않는다. 빈 입력, 불가능한 조건, 경계값, 제약을 어긴 답(거부되어야 함) 사례를 테스트로 둔다.
3. **기본안**: 가장 단순하게 유효한 답(정해진 순서의 탐욕 등)을 만들고 검증기를 통과하면 **바로 결과 파일로 저장**한다. 언제든 제출할 수 있는 결과이자 비교 기준이다. 탐욕이 막혀도 답이 없다는 뜻이 아니다. 순서를 바꾼 재시작, 백트래킹, 제약 풀이를 검토한다. 기존 결과를 개선하는 과제면 `kit/skills/improve-existing/SKILL.md`의 기준선도 쓴다.
4. 방법은 변수 유형·입력 규모·제약 구조를 보고 고르고, 이유와 버린 대안을 설계 선택 표에 적는다(결정은 응시자).
   - 조합이 적다: 완전탐색·백트래킹. 조합 수와 실행 시간을 먼저 추정
   - 유망하지 않은 조합을 일찍 버릴 수 있다: 분기 한정. 가지치기 기준이 안전한지 확인
   - 후보가 많고 빠른 답이 필요하다: 탐욕. 최적을 보장하지 않음
   - 일부를 바꿔 나아진다: 지역탐색·다중 시작, 정체되면 담금질 등
   - 제약을 식으로 쓸 수 있다: 정수계획·제약계획. 도구 설치 여부와 풀이 시간 확인
   - 상태 이동·경로: BFS·다익스트라·A*. 비용 음수 여부, 휴리스틱 조건 확인
   - 연속값: 좌표탐색·패턴탐색(미분 불필요), 경사 기반은 목적함수가 미분 가능하고 매끄러운지 확인한 뒤. 혼합이면 이산 부분을 고정하고 연속 부분을 푸는 식으로 나눈다
5. 개선 틀: 최선의 유효한 답을 보관 → 변경 후보 생성 → 제약 확인·점수 평가 → 나아지면 교체 → 시간 제한까지 반복. 더 나은 유효해를 찾으면 검증기를 통과한 것만 결과 파일로 저장한다(강제 종료·오류에도 남게). 탐색은 제한 시간에서 최종 검증·출력 시간을 뺀 시점에 끝낸다. 시간 제한·설정은 설정값으로 두고 난수 시드를 기록한다.
6. 같은 입력·제약·시간 제한으로 기본안과 개선안을 `WORK.md` "탐색 결과 비교"에 적는다: 상태, 목적값과 개선량, 실행 시간, 입력 버전·설정·시드. 점수는 검증기로 다시 계산한 값을 쓴다. 작은 입력에서는 완전탐색 결과와 비교해 정확성과 품질을 확인한다.
7. 결과는 셋으로 구분해 쓴다: **유효해**(검증기 통과, 최적성을 증명하지 못했으면 "찾은 최선의 해"), **유효해 미발견**(시간 안에 못 찾음, 시도한 방법을 적음), **해 없음**(완전탐색이나 서로 모순되는 제약으로 불가능을 증명한 경우만).

하지 않을 것: 검증기 없이 탐색기의 점수를 보고하기, 제약을 어긴 답을 점수가 높다는 이유로 내기, 못 찾은 것을 "해 없음"이라 쓰기, 결과를 파일로 남기지 않고 탐색만 돌리기.
