# 완료 주장 전에 근거 확인

1. 요구사항 목록(`TASK.md`)을 요구 하나씩 나눈다.
2. 요구마다 **무엇으로 확인할지**(실행 명령, 입력, 기대 결과)를 먼저 정한다.
3. 실제로 실행하고 **출력과 종료 코드를 읽는다.** 명령이 실패했거나 출력이 기대와 다르면 통과가 아니다.
4. 근거표(`VERIFY.md` 틀)에 요구·주장마다 아래를 적는다. 시각 순서가 아니라 요구 기준으로 쓴다.
   - 출처: 과제 안내·문서의 위치나 담당자 답변 번호. 자료에 없으면 "추정"
   - 구현·계산 위치: 파일·함수·커밋, 계산이면 명령이나 식
   - 실행 전 기대: 2번에서 정한 기대 결과. 실행 전에 적고, 결과에 맞춰 바꾸지 않는다. 손계산이 틀렸으면 원래 값을 남기고 고친 값과 이유를 덧붙인다
   - 검증 결과: 확인한 명령·입력과 실제 결과
   - 상태: 확인함 / 미검증(이유와 함께) / 실패(현상과 남은 문제) / 미확인(자료·답이 없음)
5. 구분해서 말한다. 테스트 통과, 실행 성공, 요구사항 충족은 서로 다른 주장이다. 할 일 목록을 모두 끝낸 것과 목표를 달성한 것도 다르므로, 마지막에 완료 기준 대비 충족·미충족·미확인을 따로 적는다.
   - 내가 직접 한 점검은 "자체 점검(독립 검토 아님)"이라고 적고, 독립 검토를 받은 것처럼 쓰지 않는다.
6. 서버·API·데이터 처리는 `curl`이나 테스트로 실제 응답을 확인한다. 화면 동작(입력·버튼·빈 상태·오류 상태)은 응시자가 제공된 미리보기에서 직접 확인한다. 에이전트는 확인할 항목과 기대 결과를 안내한다. 과제 안내가 허용하면 브라우저 자동화(Playwright 등)를 별도 포트·임시 DB·합성 데이터로 실행할 수 있고, 설치나 실행이 막히면 우회하지 않는다. 자동화 통과는 "자동화 확인"으로 적고 실제 미리보기 확인(iframe·쿠키 포함)과 구분한다. 응시자가 확인하지 않은 화면 동작은 "미검증"으로 남긴다. 코드에 있는 기능이 화면이나 안내에 빠져 있지 않은지는 코드와 안내문을 읽어 비교한다.

산출물: 근거표. 과제가 요구하는 문서가 있으면 표를 그 안에 옮겨 쓰고, 없고 과제가 클 때만 `VERIFY.md`로 쓴다. 별도 문서를 늘리지 않는다.

하지 않을 것: 실행하지 않은 검증을 통과라고 쓰기, 출력이 없다는 이유로 성공이라 판단하기, 서버처럼 끝나지 않는 명령을 검증 명령으로 쓰기.
