# 요구 정리와 질문 설계

1. 구현하지 않고 읽기만 한다. README·`docs`의 문서와 요청 메일은 **끝까지** 읽는다(조건이 뒤에 있을 수 있다). 설정·시작 코드·보조 파일(휴일·담당자 목록 등)도 요구에 영향을 주면 읽는다. 큰 데이터 파일은 통째로 읽지 않고 이름·헤더·몇 줄·전체 행 수를 본 뒤, 이상 징후(빈 값, 중복, 형식 불일치, 날짜 범위)를 검색이나 간단한 집계로 확인한다. 읽다가 다른 파일이 필요하면 그 파일도 읽고, 읽은 파일 목록을 정리 문서에 적는다.
2. 아래 다섯 가지로 나눠 `TASK.md`에 적는다.
   - **명시된 요구**: 문서에 그대로 적힌 것 (출처 파일 표시)
   - **미확인 정보**: 문서에 없지만 결과를 바꿀 수 있는 것
   - **가정**: 답을 받기 전까지 잠정으로 구현할 기준. "확인 전 가정"이라고 코드 주석·문서에 표시한다. 필수 필드·인터페이스는 명세를 따르고, 값을 알 수 없으면 명세가 허용하는 미확정·오류 상태로 처리하며 필드를 채우려고 사실이나 데이터를 만들어내지 않는다
   - **핵심 가정**: 가정 중 틀리면 결과 전체가 무너지는 것은 따로 표시하고, 큰 작업을 시작하기 전에 담당자 질문이나 실제 데이터 확인으로 먼저 검증한다
   - **완료 기준**: 무엇을 어떻게 확인하면 끝인지. 기존 것을 개선하는 과제면 기존 수치와 계산식(기준선)을 여기에 넣고 `kit/skills/improve-existing/SKILL.md`로 측정한다
   웹·서비스 과제면 `TASK.md`의 사용자·시나리오와 비기능 요구(성능·권한·보안·실패 대응·데이터 보존)도 과제 문구나 담당자 답변에 근거가 있는 것만 적고, 없으면 비우거나 미확인으로 둔다.
3. 미확인 정보마다 질문을 만들고 대상을 나눈다: 업무 사실은 담당자, 과제 문구의 뜻은 출제 안내 채널, 설계 선택은 응시자가 정하고(에이전트는 선택지와 추천을 낸다) 이유를 적는다.
   - 처음 1~2개는 답하기 쉬운 맥락 질문(누가, 어떤 상황에서, 무엇을 결정하려고 쓰나)으로 연다. 그다음은 결과 영향이 큰 미확인 사항부터, 실제 값이나 예시를 넣어 구체적으로, 한 번에 하나씩. 답에서 단서가 나오면 꼬리질문으로 파고든다
   - 관점: 누가 쓰나 → 화면·사용 흐름 → 입력 데이터의 이상한 점 → 계산·판정 기준 → 예외·제외 → 출력 형식 → 앞으로 반복·변경
   - 구현 방법을 묻지 않는다. "해야 할 일을 번호로 알려 달라"는 요청은 하지 않는다.
4. 담당자 인터뷰는 한 번에 질문 하나로 진행한다. `Q번호: 문장`만, 배경 설명 없이 담당자에게 그대로 보낼 문장으로 내고 멈춘다. 응시자가 답변을 붙여넣으면 `TASK.md` 질문·답변 표에 답변 요지와 상태를 바로 적고 다음 질문을 낸다.
   - 구체적인 답: 상태 확정, 관련 가정을 확정으로 올린다.
   - 모호하거나 새 쟁점: 꼬리질문 `Q3-1`, `Q3-2`(한 질문에 최대 2회), 상태 추가질문
   - 모르겠다·기준 없음: 상태 미확인. 담당자가 모른다고 한 것은 다시 묻지 않고 "확인 전 가정"으로 둔다.
   - 직접 결정해라: 선택지 2개와 추천을 보여 주고, 결과를 바꾸는 선택이면 선택지마다 결과가 달라지는 작은 입력과 기대 결과(판별 사례)를 붙인다. 응시자가 고르면 이유와 함께 설계 선택 표에 적는다(상태 설계 선택).
   - 더 물을지는 남은 불확실성이 핵심 결과를 바꾸는지, 가정으로 진행해도 나중에 되돌릴 수 있는지로 정한다. 되돌릴 수 있으면 가정으로 두고 진행한다. 답을 기다리는 동안 업무 기준에 의존하지 않는 작업(데이터 읽기, 검증 도구, 뼈대)은 진행해도 된다.
5. 인터뷰를 마치면 구현 전에 미확인을 정리한다. 가정마다 영향도(핵심/일반)와 코드 표시 위치를 적는다. 핵심 가정은 구현 전에 먼저 검증하고(실제 데이터 확인, 이미 모른다고 한 항목은 다른 경로 한 번), 일반 가정은 `확인 전 가정(Q번호)` 주석과 상수·설정으로 분리해 잠정 구현한다.
6. 기록만 근거로 문제, 만들 것·안 만들 것, 확정·미확인(가정으로 진행)·설계 선택, 성공 기준(웹·서비스 과제면 시나리오·비기능 요구도)을 한 번에 정리해 담당자에게 맞는지 확인받는다. 확인받은 것만 가정에서 확정으로 올리고, 설계 선택은 "이렇게 하겠다"로 알린다.

산출물: 요구 / 미확인 / 가정 / 설계 선택 / 완료 기준 / 질문·답변. 과제가 요구하는 문서가 있으면 그 안의 섹션으로, 없고 과제가 클 때만 `TASK.md`로 쓴다. 작은 요청은 채팅으로 답한다.

하지 않을 것: 확인되지 않은 업무 기준을 사실처럼 코드에 넣기, 질문을 한꺼번에 던지기.
